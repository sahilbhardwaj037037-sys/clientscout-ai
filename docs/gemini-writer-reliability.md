# Gemini Writer reliability repair and Stage C proposal

Historical audit/repair record: Stage A/B was implemented at Checkpoint 4. Its strict acceptance protocol has since been superseded by the user-approved [Option A](option-a-human-reviewed-writer.md). The Stage C semantic-verifier design below remains a proposal. No live Gemini request is part of either change.

## Implemented boundary

The existing annotated response protocol is retained. Gemini still returns subject/body; accepted text is persisted without rewriting or invoking the deterministic composer. Local Template and historical Gemini-assisted records are unchanged.

`writer-validator-v2` checks complete statements. It no longer removes approved substrings or globally masks business/freelancer names. Approved assertions must occur as standalone statements, with limited service-offer wrappers. Complete non-factual courtesies/questions/offers have separate bounded rules. Negation and unsupported appended clauses cannot inherit an approved substring's authority. Unknown statements fail closed. This fixes the audited false negatives; it is **not** a general semantic understanding system and can still reject harmless unfamiliar phrasing.

Three independently authored HAPPY proposals are checked in as literal JSON. They reflect the audited one-page image-alt evidence and the frontend service intersection. The freelancer name and portfolio URL are synthetic; no personal profile values, rejected live responses or secrets are fixture data. The corpus is not generated by the production composer or fact dictionaries. Paired mutations test invented problems/metrics/relationships/experience/services, guarantees, contextual negation, unauthorized domains and signatures. Existing tests still exercise quota, consent, history, editing and profile opt-in.

Diagnostics use fixed rule/reason codes and prompt/validator versions. Provider usage is captured before writing validation and persisted on the actual attempt, including failure. Only STOP responses proceed; missing/truncated/blocked/other finish states reject without fallback. No raw rejected prose or arbitrary provider failure values are retained. Parent and retry attempt states are finalized together on final-validation failure or cancellation. Successful historical jobs are not backfilled.

Profile writes enforce the same UTF-8 byte bound as reads before replacing the old file. Viewport wording now describes absence of a `width=device-width` declaration, rather than claiming absence of every viewport tag. Business names use NFC/whitespace/case normalization and word boundaries. Sender checks use trailing signature boundaries; names do not exempt other occurrences from claim checks. Explicit URL matching remains allowlisted; broader bare-domain detection and fail-closed statement validation reject undeclared destinations.

The editor ignores asynchronous results from previous assessment revisions. Automatic completion validates the origin assessment and preserves current dirty text. Explicit saved/unsaved draft navigation and manual save remain available; completion does not silently replace edits.

## Stage C: proposed contract

### Server-owned evidence bundle

Build a versioned typed bundle from current, authorized evidence:

- Observations: ID, measured predicate, subject/page scope, polarity, source/time, uncertainty and allowed interpretation. Example: `image_alt_attribute_absent`, `scope=checked_page`, `quantity=some`, never a site-wide accessibility verdict.
- Eligible offers: confirmed freelancer capability intersected with assessment eligibility; distinguish capability from an approved deliverable, schedule or free-work commitment.
- Profile proof: confirmed completed projects versus existing demos, relevance tags and allowed identity. A portfolio URL never establishes achievements or project completion.
- Link registry: opaque link IDs, exact public URLs, role (portfolio/Instagram/project), and sharing authorization snapshot.
- Identity: public business name, optional approved sender, permitted display normalizations.

Snapshot schema/prompt/validator versions and consent scope with the job. Do not expand public data sharing to raw HTML, private notes or contact values. Fix evidence meanings at the measurement-to-bundle boundary, before the writer sees them.

### Model output

Keep genuine AI-written subject/body. Remove redundant top-level finding/service/project/link declarations where the server can derive them. If annotations help the model, request a small set of statement spans with proposed supporting IDs, but treat them as untrusted suggestions. They must not decide whether their own wording is safe. The server independently segments **all** subject/body content, including clauses that were not annotated.

A candidate may contain:

1. Observed factual assertions tied to evidence predicates.
2. Capability/experience assertions tied to confirmed profile predicates.
3. Tentative suggestions/benefits with preserved modality and scope.
4. Non-factual greetings, scheduling questions, courtesies and low-pressure invitations.

The server derives used-link metadata directly from actual text, validates role/destination and records resolved IDs. It derives grounding metadata only after validating whole assertions. It never fills in missing factual sentences or silently rewrites a failure into a template.

### Identifying unsupported statements

Use layered checks rather than claiming that a keyword blacklist proves safety:

- Deterministic hard checks for URLs, identity, length, control/markup characters, metrics, entities, dates, deliverables and authorization.
- Clause-level coverage: every assertion in both subject and body must be classified; embedded presuppositions in questions/conditionals count as assertions. A polite prefix is not an exemption.
- Grounded entailment against the typed bundle: check predicate, subject, page/site scope, quantifier, negation, modality and temporal scope. Reasonable paraphrases may pass only if those properties remain supported.
- A separately evaluated semantic component for paraphrase/intent classification. Prefer a pinned local component if deployment cost/quality is acceptable. A second remote verifier would require an explicit privacy, quota and cost decision; it is not authorized or introduced here. The generating model's own confidence must not be treated as proof.
- Three outcomes internally: supported, contradicted, uncertain. Contradicted and uncertain factual assertions do not auto-persist as approved drafts. Return sanitized reasons for user action. Ordinary greetings/questions should pass without fabricated evidence IDs.

No classifier can guarantee complete semantic accuracy. Human review stays mandatory. A manual-edit workflow does not justify automatically marking fabricated AI claims as grounded. Retaining or displaying rejected text would require a separate privacy/product decision; this proposal preserves the current no-retention policy.

### Trade-offs

| Approach | Benefit | Cost/risk |
| --- | --- | --- |
| Current whole-statement gate | Deterministic, offline, auditable | Limited wording diversity; unfamiliar safe prose can fail |
| Typed predicate rules plus curated paraphrase grammar | Better traceability and scope checks | Domain-specific language maintenance; finite coverage |
| Local semantic verifier plus hard gates | Broader paraphrases without another paid request | Model packaging/runtime, calibration, versioning, false judgments |
| Additional provider verifier | Potentially broader language handling | Extra requests/cost/latency/privacy and correlated model mistakes; separate approval required |

Recommended direction: typed bundle and server-derived metadata first, then evaluate a semantic component offline. Do not remove the current safeguards before independent evidence shows the replacement improves both rejection precision and fabrication detection.

### Migration and compatibility

No database migration is required for the proposed first increment: request/result/evidence JSON can carry versioned bundles and diagnostics. Preserve existing `ai-writer-v1`, legacy selection metadata and generator descriptions. Introduce a new writer protocol identifier only when the new contract is approved; update frontend provenance rendering to recognize both. Old drafts remain readable/editable and are not retroactively revalidated or relabelled. New diagnostics must not backfill unknown historical failures.

If searchable per-statement provenance or long-term metrics later need tables, propose a separate migration with retention and rollback design. Do not create those tables as part of this patch.

### Staged verification before release

1. Approve the typed bundle, annotation contract and uncertain-output policy.
2. Add producer/consumer contract tests and measurements-to-predicate tests for every supported finding. Include long profiles, all channels, service intersections and consent changes.
3. Expand independently authored, human-labelled positive/negative pairs. Use HAPPY plus additional businesses, names, languages/Unicode and projects. Keep a held-out set that does not guide phrase rules.
4. Test negation, spelling-out metrics, pronouns, embedded clauses, deceptive links, forged annotations, metadata omissions and multiple assertions per sentence. Measure false rejection and false acceptance separately by class; do not report only overall pass rate.
5. Verify SDK cancellation/truncation/refusal/retry/usage handling, transactional failures, reload recovery and frontend navigation races with mocks.
6. Only after separate authorization, use a small bounded live smoke test to measure generator adherence. No live testing or major Stage C implementation is authorized by this patch.
